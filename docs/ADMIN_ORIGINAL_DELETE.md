# Пересылка в админ-чат: выбор оригинала и отдельное удаление

Этот PR основан на master `9081401432a5d02511b0c828c0844634dac9cada`.
Han, его пороги/обработка независимых оснований и PR #6 не изменяются.
Production-конфиги, compose и runtime-БД в рамках разработки не меняются.

## Путь оператора

SQL locator ищет по тексту/подписи или typed media key только в текущих gid и
защищаемом чате. Поля `hidden_user`, имя автора и текст не устанавливают identity
пересылки и не дают полномочий на бан. Для совпадений создаются отдельные обычные
journal cards с точными chat/message ID. Одинаковые оригиналы не схлопываются.
Новая запись hash включает gid/chat/message, legacy hash продолжает читаться;
исторические данные, уже перезаписанные прежним locator, восстановить невозможно.

Оператор сверяет чат, номер и текст оригинала и нажимает «Удалить сообщение»
именно в нужной карточке. Без нажатия оригиналы не удаляются. В текущей политике
создать и подтвердить запрос может один и тот же личный пользователь, явно
уполномоченный по **числовому** superuser ID. Username, SenderChat и общие
технические From ID не заменяют эту проверку. Другой superuser также не может
подтвердить чужой запрос. Он может отдельно нажать «Создать новый запрос» и
получить собственную карточку; прежние callbacks после этого недействительны.

Карточка — кандидат, а не доказательство, что переслан именно он. Надёжная identity
автора пересылки для такого выбора не нужна. Если автор сохранённого оригинала
неизвестен, используется `identity_kind=message, identity_id=0`: это полномочие
только на точную пару chat/message, не фиктивный пользователь. Для известного
автора сохраняется его реальная locator identity; trust/superuser/admin gates
перепроверяются при подтверждении и перед Telegram API.

Срок подтверждения — 15 минут. Максимум 20 новых запросов в минуту на gid, для
этого пути до 20 на оператора (прежний sender /spam лимит 3 не меняется).
Показать более 20 совпадений одним запросом нельзя: бот просит уточнить оригинал,
не выбирает произвольный. Неподдерживаемое медиа/альбом и отсутствие совпадений
дают русский отказ без модерации и обучения. При исчерпании лимита уже сохранённые
карточки остаются неподтверждёнными; бот сообщает о неполном сохранении.

Текст в карточке HTML-escaped, ссылки в отображаемой копии обезврежены. Исходный
текст не используется как callback authority. Callback содержит только opaque
card ref и команду; journal повторно проверяет сохранённую привязку ref,
notification chat/message ID, точного оригинала, requester и срока в транзакции.

## Примеры (синтетические)

```text
Найдено совпадений: 2. Подготовлено карточек: 2.
Выберите нужный оригинал по чату и номеру сообщения и нажмите
«Удалить сообщение» в его карточке (15 минут).
```

Для каждого совпадения отдельная карточка:

```text
🗑 Выбор оригинала — Тестовый чат
Чат: -1001234567890
Оригинал: 801
«Одинаковый текст»

Только удаление этого сообщения. Бан, очистка и обучение не разрешены.
Подтверждение ожидается до …
Удаление ещё не разрешено.
Дата оригинала: …
[Подробнее] [Удалить сообщение] [Отклонить]
[Создать новый запрос]
```

После выбора: «Решение сохранено. Фактический результат удаления появится в
карточке; бан и обучение не выполняются».

После подтверждения Telegram API: «✅ Сообщение удалено».
При `message to delete not found`: «ℹ️ Сообщение отсутствует или недоступно;
удаление ботом не подтверждено». Ручное удаление не записывается как confirmed.
После deadline: «⚠️ Требуется ручная проверка: срок выполнения истёк».

## Журнал и восстановление

`moderation_delete_requests` и `moderation_delete_request_history` — аддитивная
metadata класса полномочий и истории подтверждений;
очередь, карточки, решения, deadlines/leases/outcomes остаются существующими.
До подтверждения единственная core action — manual_review original_delete.
Dedicated `DecideDelete` атомарно разрешает ровно эту action и пишет числового
оператора. Обычный `Decide` для такой карточки отклоняет ban/undo/cleanup/learning.
Ни UpdateSpam/UpdateHam, ни изменение доверия в этом пути не вызываются.
Отказ от запроса затрагивает только его receipt, не независимые detector/Han
основания. Подтверждённый delete для chat/message не повторяется между receipts;
работающие delete lease одной пары сериализованы, включая независимый cleanup.

Дата берётся из существующего `message_dates`, а не locator observation time и
не из даты пересылки. Для legacy date=0 время не выдумывается: применяется прежний
контракт неизвестной даты и Telegram может отказать. Deadline фиксирован при
приёме: до 24 часов и, при известной дате, не позже 48 часов минус 2 минуты от
оригинала. Подтверждение/повторная пересылка срок не продлевают. 429/retry_after,
неизвестный сетевой результат, lease, deadline и рестарт обрабатывает прежний worker.
API-успех показывается только по подтверждённому результату, `absent` отдельно.

  другой оператор/чат/notification, dry/training, trust/superusers, запрет ban/undo/cleanup.
- `TestOriginalDeleteCaptionMediaAndMissingCandidates`: подпись, typed photo,
  надёжный несовпадающий forward-author, отсутствующий оригинал, safety gates.
- `TestOriginalDeleteAbsentRetryAndDeadline`: Telegram mocks, absent, 429, deadline.
- `TestDeleteRequestBoundConcurrentRestart` и `TestPostgresDeleteRequestContract`:

- `TestDeletePairSerializesIndependentReceipts`,
  `TestDeleteRequestDoesNotWithdrawIndependentModeration`: независимые действия
  не теряются и подтверждённый оригинал не удаляется второй раз.
- `TestDeleteCandidatesScopedDuplicatesAndMedia`: SQL locator SQLite/PostgreSQL,
  отдельные одинаковые originals, legacy/new metadata, разделение чатов/gid.

Четыре вручную удалённых комментария Балтии сопоставлены read-only с locator и
сохранёнными логами: один исходный chat ID подтверждён данными, по одной locator
записи на каждый message ID, без journal actions. Ветки тестов используют только
синтетические IDs/тексты; никаких повторов этих сообщений и обучения не выполнялось.

## Внедрение и откат (инструкция, сейчас не выполнять)

Перед внедрением сохранить image, env/compose diff, полные логи и согласованные
SQLite backup snapshots с integrity/SHA-256. Проверить кандидата и прежний image
на копиях, с Telegram mocks. Production-флаги Han не менять при обычном внедрении.
Переключать штатно `docker-compose down` / `docker-compose up -d`.

Откат на текущий production image 90814014 требует осторожности: прежний код
не понимает delete-only класс карточек, обычное M+ может разрешить бан/обучение.
**Не запускать прежний worker с recovery=true на новых delete-only requests.**

1. Сохранить свежие согласованные копии **актуальных** runtime-БД и экспорт
   незавершённых actions/decisions/requests, включая moderation_delete_requests
   и moderation_delete_request_history.
2. Остановить workers через `docker-compose down`.
3. Подготовить отдельный приватный rollback override, не перезаписывая текущий
   compose diff. Для всех трёх сервисов задать `MODERATION_RECOVERY: "false"`.
   При этом прежний image требует также `HAN_ENABLED: "false"`: Han требует
   recovery, поэтому этот аварийный откат временно приостанавливает и Han.
   Это существенное ограничение отката, не изменение production в этом PR.
4. Вернуть сохранённый прежний image tag; применить оба compose файла:
   `docker-compose -f docker-compose.yml -f /PRIVATE/rollback.yml up -d`.
   Проверить фактически загруженные параметры/отсутствие worker и целостность БД.
5. Не нажимать старые карточки и не пересылать сообщения для модерации до
   восстановления поддерживающего новую схему релиза. Все незавершённые операции
   остаются в текущих БД, требуют адресного review. Отключение recovery/флага
   само по себе не отменяет очередь.

Старые БД не восстанавливать, новые таблицы/историю не удалять, prune/replay не
выполнять. Возобновление recovery и Han — отдельное проверенное восстановление
с актуальными БД и прежними согласованными Han=true / ratio=0.7 / min-count=20.

## Исправления ревью: дата и новый явный запрос

Дата оригинала извлекается через существующий date locator из `message_dates`
по точной паре chat/message внутри gid. Observation time из `messages.time` и дата
пересылки не используются как MessageDate. Отсутствующий observation timestamp
(включая SQL NULL) не мешает выбору. Если настоящая дата отсутствует, сохраняется
MessageDate=0, карточка прямо пишет «Дата оригинала неизвестна». Известная дата
и абсолютный deadline удаления показываются отдельно. Недавно записанный оригинал
старше окна удаления не получает новое окно: worker завершает его как expired
без delete API.

Кнопка «Создать новый запрос» — отдельное явное решение числового уполномоченного
оператора. После истечения 15 минут или отказа она создаёт новое подтверждение;
другой уполномоченный оператор может получить собственный запрос, пока original_delete
не исполняется. Он не подтверждает чужой запрос. Текущий неистёкший запрос того же
оператора не продлевается. Повтор пересылки ничего не возобновляет.

Сохраняются прежние requester/created_at/expires_at/state/ref/notification и JSON
снимок original_delete; все прежние решения остаются в журнале. Новая карточка имеет
новый случайный ref и notification binding. Старые MD/MX/MN callbacks не приобретают
новые полномочия, в том числе после рестарта. Даже явный MN, который не создал
новый запрос, записывается как noop: его поздняя доставка не становится согласием.
Лимиты считают и текущие запросы, и архивированные подтверждения.

Новая карточка использует **ту же** core action с прежними ID, MessageDate,
attempts, uncertain и абсолютным deadline. Она не создаёт ещё одну delete-операцию.
Pending/running, confirmed, absent и неизвестный исход прежней попытки не возобновляются.
При подтверждении также проверяется независимая выполняющаяся операция той же пары;
ban/cleanup других receipts не изменяются. Новый срок подтверждения не продлевает
окно удаления, в том числе если старый deadline уже прошёл.
