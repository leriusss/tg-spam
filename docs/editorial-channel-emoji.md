# Emoji-исключение для редакционных каналов

Исключение применяется только к emoji-проверке и только для точной пары
числовых Telegram ID: исходное обсуждение и фактический SenderChat сообщения.
Оно не добавляет manual-доверие, не назначает права администратора и не меняет
MAX_EMOJI. По умолчанию список пуст: прежнее поведение сохраняется.

## Настройка (предложение для будущей публикации)

CLI: `--editorial-emoji-exemptions=-1001111111111:-1002222222222`

Эквивалентная переменная окружения:

```text
EDITORIAL_EMOJI_EXEMPTIONS=-1001111111111:-1002222222222,-1003333333333:-1004444444444
```

Все ID здесь синтетические. Формат элемента — `discussion_id:sender_chat_id`,
список разделён запятыми. Оба числа должны быть отрицательными int64, ненулевыми.
Пробелы вокруг элементов/ID допустимы; дубли не расширяют полномочия.
Имя канала, положительный user ID, ноль, переполнение, неполная пара и смешанный
валидный/невалидный список отклоняются до открытия storage или Telegram startup.
Пустая либо пробельная строка означает отсутствие исключений.

Один SenderChat может быть явно перечислен для нескольких обсуждений. Разрешение
в одном чате не действует в другом; каждый инстанс читает только свою конфигурацию.
Пара сопоставляется с собственными ChatID/SenderChat.ID текущего сообщения:
From (включая общий Telegram/Channel_Bot), username, текст, reply и forwarded
context полномочий не дают. Публикация от имени самого обсуждения сохраняет
прежний отдельный safety gate listener; это правило его не изменяет.

Оператор должен подтвердить числовую пару по данным Telegram/journal/locator.
Для связанного редакционного канала полезна проверка linked_chat_id в обе стороны.
Автоматического доверия всем каналам предполагаемого администратора/владельца нет.
Смена владельца канала не видна из SenderChat: актуальность списка пересматривается
оператором. Этот PR не запрашивает Telegram metadata и не добавляет новых API-вызовов.

## Что сохраняется

Skip применяется к одному Request через внутренний `SkipEmojiCheck` с `json:"-"`.
JSON API не может включить это исключение. Счётчик emoji и глобальный лимит не
меняются; остальные запросы продолжают получать прежний emoji-вердикт.

Проверки stopword, external inline button, CAS, meta/Lua, spacing, classifier,
similarity, duplicate, burst и Han проходят по прежним gates. Включение исключения
не подменяет обычный Check на CheckOnly, не скрывает независимые ban/cleanup,
не меняет journal/deadline/retry и не добавляет отдельного действия модерации.
Han по-прежнему не пополняет progress/ham history. Подходящий обычный ham продолжает
накапливать auto-progress по прежней политике — само исключение доверие не выдаёт.

Уже существующее manual-доверие и достигнутый auto-bypass не отзываются этим списком.
Если канал ранее получил широкое manual-доверие, для перехода именно на emoji-only
нужно отдельное явное решение об изменении доверия после внедрения; добавление пары
само по себе не сужает существующие разрешения. В этом PR runtime-доверие не меняется.

## Проверки и откат

- Parser: пустой/default, несколько пар, дубли, границы int64, невалидные/частичные
  списки fail closed; CLI и environment wiring.
- Реальный detector: восемь emoji при MAX_EMOJI=6 проходят только для точной пары;
  другой чат/канал, одинаковое имя, From/reply/forward context исключение не дают.
- Независимые stopword, external button, CAS, meta, classifier, similarity,
  duplicate, burst и Han сохраняют вердикты; ручное доверие не создаётся.
- SQLite journal и worker с Telegram mocks: emoji-only не создаёт задач,
  независимые ban/delete и burst cleanup сохраняются, повторная доставка не
  повторяет подтверждённое удаление. JSON не может установить внутренний skip.
- Полный build/test/race/lint, recovery, reporting, auto-trust и cold Chromium e2e
  выполняются CI итогового HEAD. Сетевые Telegram-действия не используются.

Изменения схемы БД и зависимостей не требуются. Быстрое отключение при будущей
публикации — пустой список; общий лимит emoji остаётся прежним. Возврат прежнего
image выполняется с актуальными runtime-БД, сохранением Han/recovery и всех данных.
Не восстанавливать старые БД, не удалять историю и не переигрывать сообщения.
Production-конфиги/compose/runtime в этом PR не меняются, merge/deploy не выполняются.
