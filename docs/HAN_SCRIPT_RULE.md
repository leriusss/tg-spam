# Настраиваемое ограничение письменности Han

Правило предназначено для русскоязычных обсуждений Балтии, Европы и Неопорта.
По умолчанию выключено; этот PR не меняет production-конфиги, флаги или данные.
Для каждого инстанса включение должно быть отдельным решением после проверки
локальной политики обсуждения. Это ограничение письменности, не определение языка:
Han используется также в японских текстах. Кириллица, латиница, арабское письмо,
корейский Hangul, греческое письмо и эмодзи сами по себе этим правилом не запрещены.

## Предлагаемые настройки

| Параметр | Значение по умолчанию | Назначение |
|---|---|---|
| `HAN_ENABLED` / `--han.enabled` | false | включить только после отдельного согласования |
| `HAN_RATIO` / `--han.ratio` | 0.7 | доля Han среди всех букв, включительно |
| `HAN_MIN_COUNT` / `--han.min-count` | 20 | минимальное количество Han-букв, включительно |
| `MODERATION_RECOVERY` / `--moderation-recovery` | прежнее значение | обязателен для включения Han |

Включённое правило требует `0.5 < ratio <= 1`, конечное число, `min-count >= 2`.
Проверка конфигурации выполняется до открытия БД. 70% и 20 — предлагаемый старт,
а не оценка точности: маленькая диагностическая выборка не даёт общей точности.

## Что считается

Считаются Unicode code points: знаменатель — `unicode.IsLetter`, числитель —
такие буквы со script `unicode.Han` стандартной библиотеки Go. Дополнительные
плоскости Unicode поддерживаются без самодельных диапазонов. Цифры, пробелы,
пунктуация, combining marks и эмодзи не увеличивают знаменатель.
Сравнение: `Han >= min-count && Han / letters >= ratio`; при `letters = 0` — пропуск.

На входе собственный `Message.Text` и подпись из существующего `transform`.
Подпись изображения не прибавляется второй раз. Telegram blockquote/expandable_blockquote
и url entities исключаются по UTF-16 offsets (подписи также поддерживаются). `Quote`, `ReplyTo`, preview,
имя автора, OCR и содержимое кнопок не добавляются. Буквальные `http(s)://`,
`tg://` и `www.` URL исключаются; видимый текст Telegram `text_link` остаётся.
Пересланные сообщения (`ForwardOrigin`) пропускаются целиком: Telegram не отделяет
в них собственный текст от оригинала. Произвольную вставленную вручную цитату
без Telegram-метаданных правило отличить от собственного текста не может.
Глобальная `cleanText`/токенизация/транслитерация не используется, чтобы сохранить
исходную письменность. Content extraction и её include-quote/reply не меняют вход Han.
Существующая multi-lang проверяет смешение письменностей внутри слов и остаётся отдельной.

| Собственный текст | Han | Все буквы | Доля | Решение Han |
|---|---:|---:|---:|---|

| `你好世界` × 7 + ` привет` | 28 | 34 | 82.35% | только удалить |

Синтетические примеры дополняют инцидент, не заменяют независимую оценку потока.

## Действия и журнал

Совпадение считается до `source=auto` bypass. Detector и burst проходят обычный
путь и сохраняют самостоятельные основания. Han не записывает auto-trust и
ham-history (`SuppressHamRecording`, без подмены обычного пути на `CheckOnly`).
Поведенческая история duplicate/burst сохраняется. Emoji-исключение редакционного
SenderChat пропускает только emoji-проверку и не освобождает от Han.

Для нового оригинала Han запрашивает два независимых persistent-действия:
`original_delete` и `ban` (для User в soft-ban режиме — `restrict`). Срок блокировки
следует существующей политике бота. Han не запрашивает обучение, массовый cleanup
или снятие доверия. Независимые detector/burst основания сохраняют свой cleanup.
Пересекающиеся операции объединяются; один оригинал не удаляется дважды.

Ban-цель берётся только из исходного Telegram update: отрицательный числовой
SenderChat либо положительный User. Shared From (136817688, 1087968824), сервисный
777000 и некорректный SenderChat не заменяются фиктивным автором. При неизвестной
цели сохраняется точное удаление chat/message, карточка объясняет невозможность
блокировки. Имена и пересылки не дают полномочий. Сохраняются manual/superuser,
self-chat, admin, dry/training и остальные действующие safety gates.

Ошибка одного действия не является зависимостью другого. Существующий общий
Telegram 429 cooldown сохраняется: retry_after может временно задержать обе
операции. Deadlines, ограниченные повторы и reconciliation прежние. Deadline
удаления — максимум 24 часа от приёма, дополнительно ограничен настоящим
Message.Date + 48 часов минус 2 минуты. Таймаут не равен подтверждённому успеху;
неопределённый SenderChat ban остаётся для ручной проверки, без слепого повтора.

## Старые и новые события

Аддитивная миграция добавляет только таблицу `moderation_han_policy(gid,since_date)`
и индекс по точному оригиналу. При первом запуске этой версии с включённым Han
записывается неизменная граница для данного gid. Миграция и worker сами не создают
новых действий. Повторный запуск, выключение/включение флага и возврат image не
переносят границу.

Ban по Han принимается только для Message.Date строго позже этой границы и не
позже времени приёма, пока оригинал ещё внутри существующего окна удаления
(48 часов минус 2 минуты). Неизвестная, будущая дата и события до границы остаются
delete-only с объяснением. Telegram хранит дату с точностью до секунды: оригиналы
в саму секунду границы консервативно остаются без Han-бана. Требуются корректные
часы хоста; observation time и дата пересылки не используются.

Перед admission транзакция проверяет существующий receipt по точной тройке
instance/chat/message, включая прежние delete-only receipts и иную identity.
Повтор самого Han ничего не добавляет и не продлевает: Han-ban, остановленный
Han demand и его deadline не возобновляются. При этом существующий receipt не
блокирует независимые detector/burst Actions: они проходят прежний merge по
своему source key, сохраняют отдельный origin и причину в карточке. Это действует
и при прежнем SenderChat-запросе, delete-only запросе либо историческом Han-only
receipt. Ручной запрос с другим ключом не подменяет независимый source receipt.
Открытие карточки только читает историю. Явное решение оператора сохраняет
свой прежний контракт (в том числе отдельное подтверждение бана/обучения).

Отдельные операции и `han:v2` demands фиксируются атомарно в том же журнале.
Старые receipts не получают этот origin и не показывают несуществующий новый ban.
Граница защищает исторические события и после обычной очистки старых receipts.
После существующей очистки receipts старше 30 дней возраст оригинала уже вне
окна удаления: такой replay не создаёт новый Han-ban. Бессрочный реестр update
не добавляется. Независимые основания сохраняют собственные прежние правила.

## Примеры карточек

Это примеры отдельных состояний, а не обещание успешного API-вызова:

```text
Преобладает письменность Han: 24 из 24 букв (100.0%); порог 70.0%, минимум 20.
Удаление: ✅ Сообщение удалено
Блокировка: ⚠️ Действие отклонено; требуется ручная проверка
```

```text
Удаление: ⏳ Удаление ожидает выполнения
Блокировка: ✅ Пользователь заблокирован навсегда
```

```text
Автор не установлен
Блокировка по Han невозможна: оригинал не содержит надёжной числовой цели User/SenderChat.
Удаление: ✅ Сообщение удалено
```

В карточке и подробностях у нового события отдельно подписаны удаление и
блокировка/ограничение; показаны фактические состояния pending, отказ, absent,
неопределённость и подтверждение. Уже отсутствующее сообщение не объявляется
API-успехом бота. Общего редизайна карточек нет.

## Внедрение и откат

Production этим PR не меняется. Предлагаемые параметры остаются Han=true / 0.7 /20,
recovery=true; флаг по умолчанию false. Перед отдельной согласованной публикацией
сохранить image, конфигурацию/compose diff, согласованные SQLite-снимки либо
PostgreSQL backup, SHA-256 и полный экспорт актуального журнала.

Прежний бинарник master `57816519` читает новую схему: существующие столбцы не
меняются. `scripts/check-han-policy-compat.sh` проверяет SQLite/PostgreSQL: новая
версия создаёт fixtures, прежний бинарник читает их, новая читает снова; состояния,
карточки, origins и граница сохраняются. Тест не запускает Telegram/worker.

Отключение HAN_ENABLED или откат image **не отменяют принятую очередь**. Старый
worker умеет исполнять её ban/delete. Неизвестная message-only authority новой
версии не исполняется прежним worker без нового Han locator; её требуется
восстановить после возврата новой версии. Не удалять таблицы и не восстанавливать
старые БД: сохранять актуальные runtime-БД, решения и незавершённую работу.

Для адресной остановки только невыполненных Han-ban/restrict:

1. Остановить workers штатным способом, сохранить актуальный журнал и backup.
2. По точному gid и сохранённому receipt проверить actions и demands. Не выбирать
   цель по тексту/имени. Сначала отработать процедуру на согласованной копии.
3. Инструмент из **новой версии**, без Telegram, вызывает Journal.StopHanBan:

```sh
go run ./tools/han-ban-stop --sqlite /exact/runtime.sqlite --gid exact-instance \
  --receipt 'source:-100:123:user:456' --apply
# PostgreSQL: вместо --sqlite использовать защищённую переменную HAN_STOP_POSTGRES_URL.
# Пароль не помещать в команду/логи; остальные аргументы те же.
```

4. Проверить экспорт: только active `han:v2` demand банов/restrict в pending/running
   снят; delete и detector/report/operator demands остаются. Если есть независимое
   основание, ban законно остаётся в очереди. Не выполнять массовую отмену по kind.
5. Уже отправленный running запрос невозможно отозвать. Подтверждённый исход
   остаётся confirmed; неизвестный исход требует ручной проверки. При ранее
   отправленном запросе остановка worker не доказывает отсутствие эффекта.
6. Возвращать сохранённый image с актуальными БД. Подтверждённый ban не снимается
   откатом; разблокировка — отдельное явное решение с существующими safety gates.

Инструмент не снимает trust, не учит модель и не меняет delete. На работающем
worker остаётся гонка с уже прошедшей авторизацией, поэтому сначала остановка.
Дубли старого update не возобновляют остановленный Han-ban. Новое явное решение
оператора может создать собственное независимое основание.
