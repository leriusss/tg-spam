# Экран «Подробнее» модерации

Это изменение представления и навигации. Политика Han, граница новых событий,
независимые ban/delete/cleanup, recovery, retry/deadline, trust, emoji-исключения,
training/dry и смысл операторских подтверждений не меняются. Production этим PR
не меняется. Новых таблиц, колонок и миграции истории нет.

## Операторский экран

«Подробнее» начинает с результата, понятной причины и отдельных исходов действий.
Для User показан «Пользователь», для SenderChat — «Канал», при ненадёжных/неполных
сведениях — «Автор не установлен». Отсутствие запроса на ban не представляется
как доказательство текущего Telegram-статуса автора.

Han объясняется как письменность: сохранённые числитель, знаменатель, доля и пороги.
Отдельные детекторные основания и запросы на решение оператора не смешиваются.
Если подробностей события нет, явно показано «Подробный разбор проверок не сохранён».
Персональная последняя детекция locator.Spam не подставляется в старую карточку:
она могла относиться к иному сообщению.

Сохранённые причины emoji, classifier, similarity, CAS, duplicate/burst и остальные
встроенные проверки имеют русские объяснения. Emoji показывает сохранённые количество
и лимит, similarity — коэффициент и порог, classifier — вероятность и только явно
записанный порог. Текущая версия детектора пишет вероятность classifier без порога:
настройки текущего запуска не подставляются в историю. Счётчики/доли вне допустимого
формата или диапазона не выдаются за достоверные числа.

Распознаются строки Response.String (`name: spam|ham|error, details`, также с `- `)
и положительный конверт `Независимое основание модерации: name — details` существующего
writer Han. CAS считается основанием только при сохранённом положительном вердикте;
ошибки, отрицательные ответы и имя проверки без вердикта не доказывают спам.
Ошибочные/противоречивые старые записи помечаются явно. Неизвестный формат получает
«Сохранённую причину не удалось достоверно распознать», без выдуманного автоматического
основания. Безопасно экранированная исходная причина остаётся в технических данных.
Отсутствующие причины не восстанавливаются из текста сообщения, locator или текущих
настроек; сохранение новых типов данных и политика детектора этим UI не меняются.

Результаты берутся из состояний/флагов журнала, не из текста ошибок. Absent не
означает удаления ботом; uncertain не становится успехом; закрытие ручной работы
помечено около действия и не меняет результат API. После unban/restore учитывается
более позднее решение существующей проекцией currentCardActions. Снятие требования
не объявляется отменой отправленного запроса.

Совет оператору появляется при незавершённом запросе, доступном автоматическом
повторе или проблеме. Повтор не обещается за deadline/бюджетом попыток. Действия
не появляются из просмотра. «Изменить бан» доступно только при связанной ban/restrict
записи; существующее M+ без такой записи подписано «Запросить блокировку и удаление».
MA сохраняет сценарий явного снятия блокировки/ограничений, но подтверждение теперь
подписано по смыслу; новые полномочия не добавлены.

Исходный текст отдельно экранирован и ссылки сделаны неактивными, preview отключён.
Эти изменения относятся только к отображению; Card.Text для обучения не меняется.
Message.Date берётся из точного original_delete либо существующего date locator
для chat/message. RecordedAt и observation time не заменяют дату оригинала.
Название чата в текущей схеме карточки не сохранялось: честно показано «название
не сохранено», идентификатор доступен в диагностике; текущий конфигурационный label
не выдаётся за сохранённое историческое имя.

## История и границы сохранённых данных

ReadCardView читает согласованный read-only snapshot (SQLite / PostgreSQL repeatable
read) без записи moderation_control, actions/demands/decisions или новых событий.
Прежний CardView бизнес-решений сохраняет существующую транзакционную семантику.

Используются имеющиеся created_at события, accepted_at оснований, closed_at ручных
закрытий, записи decisions и история delete-request с её сохранёнными snapshots.
Подтверждения API и отдельные попытки не имеют отдельного timestamp в старой схеме.
next_at — время планирования, **не** дата подтверждения; его нельзя подписывать
«Telegram подтвердил в …». Для таких исходов указано неизвестное время. Attempts —
счётчик обработки журнала, а не число строк логов и не доказательство N сетевых отказов.
Сохранённые действия упорядочены по записи планирования, датированные записи —
по сохранённому времени; полную хронологию неизвестных дат восстановить невозможно.
Архивы запросов и все действия доступны на страницах, без усечения общей строки.

## Диагностика и навигация

- M? открывает операторский экран; MP<page> меняет его страницу.
- MT<details-page>.<technical-page> открывает «Технические данные».
- Диагностика возвращает на исходную страницу MP, а MB — «← К карточке».
- Все переходы редактируют то же сообщение; «Подробнее» внутри подробностей нет.
- Сохраняются destination/bound-message/ref проверки, числовые superuser gates
  запросов, защита superseded callbacks и ограничения dry/training.
- Общий доступ к обычной карточке остаётся в рамках существующего доверенного
  админ-чата; доступ к SenderChat/delete-request дополнительно числовой, как прежде.

В диагностике подписаны IDs, origins/demands, внутренние states/codes, attempts,
deadlines, next_at, lease, записи решений и архивные сведения. Общего fmt-дампа map
или Go-структур нет. Токен-подобные значения и credential URL маскируются.
Результат не выводится из произвольного diagnostic текста.

HTML строится из отдельно экранированных фрагментов. Пагинация считает UTF-16
с запасом до лимита Telegram; заголовок и текущие исходы повторены для контекста.
HTML/Unicode не обрезаются по байтовой границе. У очень длинных причин/действий
полные сведения продолжаются на следующих страницах.

## Примеры и воспроизведение

[Каталог текстовых и PNG-примеров](examples/moderation-details/README.md).
Все значения синтетические. Это HTML-предпросмотр настоящих Go renderer-функций и
клавиатур, а не скриншоты Telegram-клиента. Шрифты и переносы в Telegram могут отличаться.

```sh
DETAILS_PREVIEW_DIR="$PWD/docs/examples/moderation-details" \
 go test -short -count=1 -run '^TestOperatorDetailsFixturesAndExport$' ./app/events
npm ci --prefix tools/playwright --ignore-scripts --no-audit --no-fund
# Используется уже установленный Chromium проекта либо CHROMIUM_EXECUTABLE_PATH.
node tools/moderation-details-preview/render.cjs docs/examples/moderation-details
```

Зависимости Go/npm и их версии не изменены. Экспортный тест проверяет fixtures и без
переменной экспорта; PostgreSQL запускается полным Linux CI. Дополнительно проверены
все переходы с Telegram mocks, неизменность SQL, возврат страницы из диагностики,
expired/rejected/superseded запросы, неверный пользователь/чат/anchor, Unicode,
экранирование, токены, лимиты и отсутствие обещания повтора после deadline.

Откат UI — прежний image с актуальными runtime-БД: схема и история этим PR не
меняются. Merge/deploy и любые реальные Telegram-действия в этой задаче не выполняются.
