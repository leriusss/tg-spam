## Хранение и миграция

Одно nullable-поле `approved_users.auto_progress TEXT` хранит JSON:

```json
{"count":0,"chats":{"-100":{"count":2,"messages":[17,18]}}}
```

`chats` содержит фактически зачтённые сообщения отдельно для каждой исходной chat identity.
Внешний ключ `(gid,uid)` остаётся прежним; положительный user ID и отрицательный SenderChat ID различаются.
`count` предназначен для library/HTTP callers без Telegram identity (ChatID=0, MessageID=0).
Эта область не даёт доверие другому чату. `Meta.ChatID` передаётся из настоящего `OnMessage`;
message ID без chat ID не считается надёжной идентичностью. Частичная identity не даёт increment и видна в checks.

Миграция выполняется обычным NewApprovedUsers внутри существующей SQL transaction. Для SQLite и PostgreSQL
используется проверка metadata перед ALTER; повторный запуск безопасен. Существующие строки, id, name, timestamp
и source не переписываются. NULL progress означает ноль. Для самых старых схем без uid/gid сохранена миграция
прежнего id в uid, с последующим уникальным индексом `(gid,uid)`. Повреждённый JSON/отрицательный count
вызывает явную ошибку загрузки, а не доверие по умолчанию.

| Сохранённая строка | До исправления после рестарта, N=3 | После исправления |
| --- | --- | --- |
| source=manual | Присваивался count=4, bypass | Явное ручное доверие, независимо от count/порога |
| source=auto, старый NULL progress | count=4, bypass | Нулевой прогресс; следующие три подходящих сообщения проверяются |
| source=unknown, NULL/empty либо иной source, старый NULL progress | count=4, bypass | Нулевой прогресс; явного доверия нет |
| auto/unknown с сохранённым прогрессом 1 или 2 | Старый binary игнорирует progress, назначает 4 | Восстанавливается 1 или 2 в том же source chat |
| auto/unknown с сохранённым прогрессом 3 | Старый binary назначает 4 | Восстанавливается 3; четвёртое сообщение получает bypass |

Неизвестный source не приравнивается к manual. После будущей полной ham-проверки прогресс неизвестной записи
может расти, но её source остаётся прежним, включая NULL/empty и нестандартные значения в БД.
Для нового пользователя создаётся source=auto. Исторические сообщения не перечитываются и не модерируются.
Порог может меняться между запусками: сравнивается фактический count с новым порогом; достигшие его пользователи
периодически не перепроверяются. Изменение конфигурации одновременно с Check не поддерживается.
Метод IsApprovedUser для report eligibility сохраняет прежний строгий `count > N`; detector bypass использует `>= N`.

## Конкуренция, ошибки и повторы

Все завершённые eligible ham checks сериализуют только read-modify-write прогресса отдельным trust mutex.
Модель и map защищены существующим RWMutex; запись под RLock устранена. CAS/OpenAI/meta checks выполняются
до захвата trust mutex, под read-блокировкой модели, без глобальной write-блокировки на время внешних проверок.
Add/Remove/Reset/WithUserStorage используют тот же порядок блокировок. Возвращаемые UserInfo имеют deep copy прогресса.
Несколько начатых до достижения порога проверок могут завершиться и увеличить count выше N: каждая действительно проверена.
Spam, CheckOnly, rune-short сообщения и недоступная статистическая модель не увеличивают прогресс.
Существующий meaningful-token guard и прочие условия проверки не расширены.

Один SQL UPSERT сохраняет count и окно replay вместе, сохраняя id существующей строки.
Память публикуется только после успешного Write. Ошибка Write оставляет прежние count/replay в памяти;
возвращается check `auto approval persistence` с Error и запись WARN. Это не spam-решение.
После восстановления storage следующая полная проверка может быть зачтена. Ошибка удаления возвращается,
а память очищается только после успешного Delete, поэтому не возникает скрытого восстановления старого доверия при рестарте.

Память и SQL **не являются одной транзакцией**: остановка после SQL commit до публикации памяти оставляет сохранённый
зачтённый прогресс; рестарт читает его. Если драйвер вернул ошибку при фактически выполненном commit, память остаётся ниже,
а повторная запись той же версии не прибавляет второй increment в БД. Нет гарантии для нескольких detector/process,
одновременно пишущих один gid: штатная архитектура — один detector на instance. Ошибка стороннего adapter без
реального сохранения count не исправляется библиотекой; built-in SQLite/PostgreSQL поддерживают полный контракт.

Окно из последних 128 зачтённых message ID на `(gid,user/sender_chat,source_chat)` сохраняется с count.
Повтор в этом окне, в том числе после рестарта, не увеличивает прогресс; текст не используется как identity.
Порядок доставки не важен. Это ограниченная защита, не бессрочный журнал всех Telegram updates:
повтор вне окна при N>128 может быть зачтён снова. При обычном N=3 bypass прекращает накопление задолго до вытеснения.
Удаление пользователя очищает его прогресс и окно; новые сообщения начинают накопление заново.
Callers без обоих идентификаторов не могут получить identity-based deduplication и должны использовать CheckOnly
для повторных диагностических запросов. Защита не меняет moderation journal/retry/dedup действий.

## Проверки

Настоящие SQLite adapters: закрытие/повторное открытие после 0/1/2/3, последовательные рестарты, переход порога,
ручные и неизвестные записи, Write failure/recovery, удаление, параллельные уникальные и повторные сообщения,
раздельные chat/user/SenderChat, настоящее OnMessage и недоступная модель после обучения.
Migration-тест StorageTestSuite запускается также с настоящим PostgreSQL вне short-режима.
Сетевые проверки заменены mocks; production-БД, Telegram API и реальные moderation actions не используются.

`scripts/check-approved-progress-compat.sh` создаёт только fixtures и компилирует старый adapter/detector из точного
production commit. Он проверяет SQLite и, если передан COMPAT_POSTGRES_URL отдельного тестового PostgreSQL,
обе схемы: новый код сохраняет count=2, старый binary читает новые строки без schema error и воспроизводит старый bypass,
новый binary повторно читает тот же count=2. URL рабочего PostgreSQL передавать запрещено.
Workflow auto-trust-progress включает SQLite/PostgreSQL race, build, changed-code lint и эту проверку старого бинарника.

Результаты выполненных команд и CI добавляются в draft PR. Windows full-suite ограничения и прежние lint/setup ошибки
учитываются отдельно от целевых проверок; исключённые либо не выполненные проверки не считаются PASS.

## Будущее внедрение и откат

В этой задаче внедрение не выполняется. После отдельного разрешения: сохранить старый image/binary, исходники,
полные логи, конфиги/env/mounts/compose diff и согласованные SQLite online backups либо PostgreSQL snapshot;
проверить integrity и SHA-256. На копиях применить migration, проверить manual/auto/source агрегаты и старый binary.
Затем штатный запуск кандидата выполняет additive migration автоматически; словари/порог/compose не менять.
Следить за загрузкой пользователей, ошибками progress persistence, polling и recovery worker.

Откат — возврат прежнего image с **актуальными runtime-БД**, без удаления колонки, восстановления старых БД и replay истории.
При принятом для ATAS внедрении использовать только docker-compose down / up -d, сохранить recovery и compose diff.
Возврат прежнего бинарника **возвращает прежний дефект доверия**: schema compatibility не исправляет старую версию.
После работы старой версии часть SQLite progress может стать NULL из-за её INSERT OR REPLACE; повторный переход
на исправленную версию трактует это как неизвестный нулевой прогресс, без повышения доверия.
Для отмены только исходников — revert feature commit; исходный master доступен в приватном bundle/архиве.
